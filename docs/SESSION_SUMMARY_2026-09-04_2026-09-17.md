A correctness scare worth recording: pinned split repeats initially diverged in decode logits. An unsafe path was also found and gated: shared-expert allocations could trim expert slabs while selected uploads still targeted them. Prefill shared/upload overlap is now opt-in only and remains off.

## Phase 3: why the server was slower than the CLI (Sep 7)

The user reported a real Pi session at `ttft 53338ms prefill 63 tok/s decode 7.5 tok/s`. The CLI benchmarks said 10 t/s steady. Two separate explanations were established, neither of them a regression:

The 53-second UI number was the second of two tool follow-ups, not the initial request. The initial 8920-token prompt took 145 s of prefill. The number the user saw belonged to a later 818-token turn.

The rest was deliberate server behaviour. `openai_stream_start()` sets `guard_second_reasoning` when thinking and tools are both enabled, withholding ordinary answer text until a tool marker, a second `</think>`, or completion. Upstream introduced this in `fe2d3b0` to stop malformed second-reasoning leakage and closed issue #678. A temporary repro confirmed the interaction, and existing second-reasoning tests would break if the guard were simply removed. Nothing was changed.

A fresh server replay then found the actual throughput problem: only 6.10 GiB of experts stayed resident despite the configured budget, with 48370 of 99072 selections missing. Retained prefill weight ranges were occupying VRAM that the decode expert cache needed. The phase-boundary reset in `c229363` raised residency to 13.83 GiB, cut misses to 30694, and moved the sampled server replay from 7.15 to 8.99 t/s overall (7.17 to 9.19 t/s after the first logged interval) with identical generated output.

## Phase 4: the crash (Sep 7)

`ds4-server` aborted twice in one afternoon, at 14:34 and 18:58, both mid-decode in the streaming upload path. The assertion was `stl_vector.h:1253`, `__n < this->size()`, inside `libhsa-runtime64`.

Symbolized from the core with debuginfod: `rocr::AMD::BlitSdma<true>::PendingBytes()` at `amd_blit_sdma.cpp:1183`. The ring index is masked into an 8 MiB ring and then rounded up to a `uint64_t` index. An offset of `0x7ffffc` maps to index 1048576, which is one past the end of a vector holding exactly 1048576 entries. The exact offending offset was optimized out and is not proven, but garbage pointers or a concurrent engine-destroy race are not required to explain the assertion.

A second error in the original crash report was corrected at the same time: the process was running the RAM-backed model, not the NVMe one. The post-crash hook then unmounted `/mnt/ram`, so the tmpfs copy was lost. The NVMe original was untouched and has since been restored.

This remains open. `HSA_ENABLE_SDMA=0` is a candidate workaround and its throughput cost is unmeasured.

## Phase 5: thinking loops (Sep 7)

The user reported the model repeating a planning paragraph indefinitely. Diagnosis offered: repetition degeneration, where a dead-end plan ("I need a source but do not know the URL") gets re-emitted instead of the model taking an action or qualifying its answer. Contributing factors listed without proof: long context, steering scale 3 acting globally rather than as a refusal-specific switch, thinking mode collapsing low/medium/high to HIGH, and the possibility of a genuine inference defect that short equality tests would not catch. A prompting remedy was provided. No code change was made.

## Phase 6: upstream and model investigations (Sep 10 to Sep 16)

Upstream checks, in order, produced three corrections of earlier claims:

- Sep 10: 76 commits behind. Highlights were vision context preservation across tool calls, agent compaction recovery, ROCm memory budgeting, GLM attention fixes.
- Sep 13: the answer "no 4.1" was wrong because the fetch was stale. A re-fetch found `bd66c40 DeepSeek v4.1 Flash support for Metal`, 521 files, 1.16M insertions.
- Sep 16: 54 more commits, now 131 behind. `a04f46f` added V4.1 CUDA support for DGX Spark, and Qwen3.8 Flash Next landed for Metal and CUDA.

V4.1 status across all of it: Metal text and vision, CUDA text only, **ROCm not implemented**, no DSpark, no pipeline execution. Qwen3.8 Flash Next: also no ROCm, and no SSD expert streaming.

Two corrections of my own analysis were issued in this phase. First, the "no payoff on this hardware" claim about V4.1 was unsupported, because RAM shortfall does not rule out SSD streaming, Engram reads are sparse rather than sequential, and an upstream port would supply the tokenizer, graph and CUDA reference. Second, the small-model shortlist of GLM-4.7-Flash and Qwen3.6-35B-A3B was withdrawn once the user's actual llama.cpp lineup was inspected and shown to be stronger than assumed.

The user then stated the real goal: a model that runs on ds4 and not on llama.cpp, or is faster on ds4, and is at least equal in quality to what is already served. No candidate currently satisfies all three conditions on the evidence available.
